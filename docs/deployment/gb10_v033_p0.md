# GB10 Engram P0 experiment on the v0.33 EXL3 compatibility base

This branch adds three opt-in features to the validated common base at
`98cdfeae38899fa606245a850026ddd6566eeccf`. Common compatibility fixes are
documented in [the baseline recipe](gb10_v033_exl3.md). They are shared by A and B.
No scheduler, KV capacity, attention algorithm, quantization or speculative
decoding policy changes are part of this experiment.

## Physical rank-local packs and manifest

Run the offline tool separately on each rank, using the same checkpoint and
the native vLLM hash-head layout:

```bash
python -m vllm.models.deepseek_v41.common.engram_prepare \
  --model /model --output /engram-pack --tp-size 2 --tp-rank 0
```

Use the image's virtual-environment Python. Rank 1 uses `--tp-rank 1`.
Each local manifest contains only that rank's layers. Both nodes mount their
own directory at `/engram-pack`; files do not need to be replicated across TP.
The format is versioned: a 4096-byte header followed by 512-byte records
containing 256 raw FP8 bytes, eight raw UE8M0 bytes, and zero padding.
No dequantization or scale recoding is performed. Padding costs disk space:
roughly 183 GiB per rank for this checkpoint, versus 94 GiB of useful row data.

The writer streams bounded chunks into exclusive `.part` files, fsyncs data,
renames completed files, verifies full SHA256, and finally publishes the
manifest atomically. An interrupted `.part` is never a valid pack. Inspect an
incomplete artifact before retrying; the tool does not silently overwrite it.

Runtime checks checkpoint/tokenizer identity, TP rank, layer, row range,
geometry, source headers, file length, pack header, sampled raw source rows and
sampled pack hashes. `disk_verify="full"` additionally hashes the complete pack.
`"sample"` avoids a full startup scan; it does **not** promise detection of
arbitrary unsampled corruption. Offline full verification and runtime sample
verification are distinct recorded events. Source payload binding is sampled,
not a second full comparison of the original checkpoint payload.

## Direct I/O reader

```json
{
  "cpu_offload": true,
  "dp_shared_memory": false,
  "disk_offload": true,
  "disk_threads": 32,
  "disk_pack_manifest": "/engram-pack/manifest.json",
  "disk_cache_bytes": 16777216,
  "disk_verify": "sample",
  "disk_stats_dir": "/p0-output"
}
```

`disk_cache_bytes` bounds each layer's row data, tags and cache locks.
Sort/group staging and per-thread direct-I/O scratch are separately reported.
The example uses 16 MiB per layer because the common base has little UMA
headroom. A zero cache disables row caching. The default manifest path is absent,
so legacy checkpoint disk offload remains available without enabling P0.

The reader sorts and deduplicates requested valid rows, reads each cache miss
once with O_DIRECT, restores original ordering, and preserves padding behavior.
Large prefill batches bypass cache admission. Filesystem alignment is checked
with statx and an actual direct read; unsupported direct I/O fails explicitly.
There is no buffered fallback that can consume an unbounded page cache.

The existing CUDA host-node and vLLM lookup kernel remain the execution path.
Pinned buffers and captured jobs remain stable across graph replay. Native
counters report actual host-node executions, unique rows, hits and disk bytes;
Python graph capture is not counted as a completed read. Optional JSONL counters
are sampled every ten seconds and should be enabled consistently across B runs.

A short read or I/O error latches failure. A device assertion placed before the
lookup kernel checks status on every graph replay. This intentionally terminates
the worker's CUDA context; restart the worker after repairing the artifact.
It is not a recoverable per-request error and never silently substitutes zeros
for failed valid reads.

## UMA budget preflight

The standalone `engram_preflight.py` script calibrates an empirical memory envelope
from an A observer resource log, then evaluates the same recipe with bounded B
allocations added. It uses `MemTotal - MemAvailable` once. CUDA memory, process
RSS, weights and KV are not added again on a unified-memory device.

```bash
python /usr/local/lib/python3.12/dist-packages/vllm/models/deepseek_v41/common/engram_preflight.py \
  --model /model --recipe /recipe/recipe.json --profile /recipe/uma-A.json \
  --calibrate-resources /observation/resources.jsonl --validated-context 64890
python /usr/local/lib/python3.12/dist-packages/vllm/models/deepseek_v41/common/engram_preflight.py \
  --model /model --recipe /recipe/recipe.json --profile /recipe/uma-A.json \
  --cache-bytes 16777216
```

Execute the script by file path. Using `python -m vllm...` initializes the parent
package and PyTorch, whose transient process memory can distort a tight budget.
The file-path entry point uses only the standard library.

Profiles bind checkpoint identity, common engine arguments, TP rank and UMA
capacity. Explicit reserve and sampling-margin arguments are deployment policy,
not measurements. Defaults are conservative: 8 GiB reserve plus 4 GiB margin;
the tight GB10 recipe can fail this policy even when A previously ran.
Any reduced policy must be recorded with its actual values. Insufficient
available memory returns exit code 2; a larger configured context than the
validated envelope returns `WARN_UNVALIDATED_CONTEXT`. This warning is not a
capacity or full-context validation pass. The tool changes no engine settings.

The initial functional acceptance covers 64,890 prompt tokens while configuring
a 512K ceiling. It does not establish successful 512K requests or performance
gains. Formal A/B performance measurements are a separate user-controlled step.

## Provenance and verification

The direct-I/O layout, sort/unique reads, bounded cache admission and atomic
pack/manifest design were informed by TensorFold source revision
`93a2e93ecebff8aa52b88e58c5dd222516e69c5f`, specifically
`engram_rows_linux.zig`, `engram_pack.zig`, and `engram_manifest.zig`.
This is a vLLM implementation preserving its hash layout and lookup semantics;
TensorFold pack binaries are not interchangeable with this format.

CPU file-format and memory-policy tests live in `tests/kernels/test_engram_pack.py`.
`test_engram_disk_rows_refresh_on_graph_replay` compares resident, checkpoint and
pack paths for BF16 and exact packed output, including duplicate IDs, padding,
scale edge bytes and new IDs on every replay. The isolated graph fault test
truncates a real file after capture and requires a device assertion.
The existing miscellaneous-kernels CI job selects both root-level test files.
Hardware acceptance additionally requires the same real TP2 API, streaming,
concurrency, reasoning, tool, image and long-prefill checks used for A.
